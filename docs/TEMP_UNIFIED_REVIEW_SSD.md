# 临时 SSD：完成后复盘与自进化统一设计

本文件只用于本轮方案确认。用户确认后，再把核心原则合并进 `ECROOM_SSD.md` 并执行前后端改造。

## 1. 重新定义问题

当前产品里存在两条相近但分裂的线索：

- `完成后可选沉淀`：让用户决定是否保存本次创作中暴露出来的偏好、项目规则或风格要求；
- `是否调整我的工作方式`：让用户决定是否允许 EcRoom 根据失败信号改进自己的工作规则。

它们不应该是两个视觉模块。它们本质上都是一次创作完成后的复盘问题：

```text
这次创作结束后，有哪些东西值得带到以后？
```

区别只在于“带到以后”的对象不同：

| 类型 | 改变什么 | 用户实际在确认什么 |
| --- | --- | --- |
| 偏好沉淀 | EcRoom 记住用户或项目 | 以后类似创作要不要参考这条偏好/规则 |
| 工作方式调整 | EcRoom 改进自己的协作流程 | 以后类似创作时，助理要不要换一种处理顺序或检查方式 |

因此，新的设计不再把二者拆成两个面板，而是合并为一条 `完成后复盘` 功能线索。

## 2. 产品命名

用户侧不使用“自进化”“harness”“manifest”“LearningCandidate”等工程词。

推荐用户可见命名：

- 主入口：`本次复盘`
- 徽标文案：`3 条可确认`
- 弹窗标题：`这次有什么值得保留？`
- 偏好类条目：`记住这个偏好`
- 项目类条目：`保存为项目规则`
- 工作方式类条目：`调整助理工作方式`
- 跳过动作：`跳过`
- 技术折叠区：`为什么会建议这条`

内部仍可保留 `learning`、`evolution`、`harness` 等模型名，但前端主文案必须翻译成用户能判断的协作语义。

## 3. 触发时机

复盘只在用户明确结束一个话题或确认一个版本可用后出现。

触发入口：

```text
用户创作中
  -> 系统只记录内部观察和失败信号
  -> 用户点击“完成作品”或“结束这个话题”
  -> 后端生成复盘队列
  -> 对话角落出现小图标/小徽标
  -> 用户点开后逐条确认
```

禁止行为：

- 创作过程中弹出大面板；
- 输入框下方长期占用空间；
- 默认自动打开复盘弹窗；
- 用户还在改稿时要求处理记忆和工作规则；
- 把一次临时要求直接写成长期偏好或全局工作方式。

## 4. 视觉与交互

### 4.1 入口位置

入口使用小图标，而不是大面板。

位置建议：

- 放在当前对话结束区域或最后一条 assistant 回复的右上角；
- 也可放在输入框右上角的非主操作区域；
- 有待确认项时显示数量徽标；
- 无待确认项时隐藏。

入口示例：

```text
[小图标] 本次复盘 3
```

它不应该挤压消息、输入框或主创作区。

### 4.2 弹窗结构

点击入口后打开居中弹窗。弹窗不分成多个大模块，而是一条队列：

```text
这次有什么值得保留？
1 / 3

类型：记住这个偏好
建议：以后写角色登场文案时，先保留角色冷面、克制的气质，再做平台化改写。
为什么：这次用户多次要求“别太热闹”“不要像营销号”。
以后影响：类似角色宣发会优先保持人设稳定。
适用范围：当前项目 / 类似角色内容 / 全局偏好

[跳过] [保存这条]
```

工作方式类条目示例：

```text
类型：调整助理工作方式
建议：以后处理角色宣发时，先检查角色设定和时间线，再改成平台发布版本。
为什么：这次返修集中在“角色不像自己”和“平台化太早”。
以后影响：类似任务会多一次设定一致性检查，减少跑偏。
适用范围：当前项目 / 类似叙事内容

[跳过] [允许这样调整]
```

每次只展示一条，用户点击任意按钮后进入下一条。处理完后关闭弹窗并隐藏徽标。

### 4.3 不再保留独立 `learningPanel`

原来的 `完成后可选沉淀` 面板会造成和工作方式入口重复。执行实现时应移除或转化为统一复盘入口：

- 不再在对话区下方展开学习面板；
- 学习候选进入同一个 Review Queue；
- 原 `learningList` 的卡片内容转为复盘队列里的 `memory` 类条目；
- 原 `evolutionReviewBtn` 继续作为入口，但语义改为 `本次复盘`，不只代表工作规则。

## 5. 复盘条目模型

前端不应直接拼接两套数据。后端应提供一个统一的复盘条目 DTO。

```text
ReviewItem
  item_id
  session_id
  source_type: memory | project_rule | assistant_workflow
  title
  suggestion
  reason
  evidence_summary
  impact
  suggested_scope
  allowed_scopes
  confidence
  status: pending | accepted | skipped | blocked
  technical_ref
```

其中：

- `memory` 来自 `LearningCandidate`，保存后进入偏好记忆；
- `project_rule` 也是学习候选，但作用域锁定为当前项目或项目资料；
- `assistant_workflow` 来自 `EvolutionProposal`，保存后进入工作规则调整流程；
- `technical_ref` 保存 candidate id、proposal id、manifest path、validation plan 等，不在主界面展示。

## 6. 自进化分层

EcRoom 的自进化不是“自动改 prompt”，而是三层变化都可解释、可撤销、可评测。

```text
第一层：本次对话内适应
  用户继续反馈，系统立刻改稿。
  不需要用户额外确认，不写入长期系统。

第二层：完成后记忆沉淀
  用户确认某条偏好或项目规则值得保留。
  后续相关任务可召回，但受 scope 限制。

第三层：助理工作方式调整
  系统发现重复失败或明确改进点。
  需要证据、作用域、A/B 或人工说明，用户允许后才应用。
```

这三层共同构成“自进化”，但它们不能混在一起：

- 对话内适应最快，但只影响当前会话；
- 偏好沉淀影响后续创作，但只代表用户/项目需求；
- 工作方式调整影响 agent/harness，但必须更保守，因为它改变的是系统行为。

## 7. 作用域规则

所有复盘条目都必须有作用域，且默认保守。

| 条目来源 | 默认作用域 | 可升级条件 |
| --- | --- | --- |
| 临时措辞、单次修辞要求 | 不进入复盘 | 用户明确说以后都这样 |
| 多次出现的风格偏好 | 当前项目或类似内容 | 多次确认后可全局 |
| 角色、人设、世界观 | 当前项目 | 用户明确设为通用创作原则 |
| 平台规范 | 对应平台任务 | 平台规则稳定且多次验证 |
| 工作方式调整 | 当前项目或类似任务 | A/B 通过并多次人工确认 |

用户可在弹窗里选择更小的作用域，但不应默认给“全局”强提示。全局只在证据非常明确时出现。

## 8. 接受与跳过语义

### 8.1 用户点击保存/允许

根据条目类型执行不同后端动作：

| source_type | 按钮文案 | 后端动作 |
| --- | --- | --- |
| memory | 保存这条 | `LearningStore.apply(action=preference)` |
| project_rule | 保存为项目规则 | 写入项目作用域 memory 或 knowledge rule |
| assistant_workflow | 允许这样调整 | `EvolutionProposal.apply`，仍受 gate 限制 |

如果工作方式条目缺少足够评测，不能直接写入 harness，应进入 `blocked` 或 `needs_validation` 状态，并告诉用户：

```text
我会先把它作为待验证的改进点保留，证据足够后再应用。
```

### 8.2 用户点击跳过

跳过不是负反馈，也不是删除证据。

- memory/project_rule：状态变为 `ignored`，不进入召回；
- assistant_workflow：状态变为 `ignored`，当前会话不再提示；
- evidence 继续保留，用于未来统计，但不得单独触发全局变化；
- 如果类似问题多次出现，系统可以以后用更清楚的证据重新提出。

## 9. 设置页中的位置

设置页不应成为主要复盘入口，只提供管理能力：

- `个性化`：查看已保存偏好，删除或调整作用域；
- `数据管理`：说明对话、作品、偏好、项目资料、复盘建议分别存在哪里；
- `工作规则`：控制是否允许系统生成复盘建议、是否记录技能运行、最低评测要求。

也就是说，设置负责管理长期结果；对话角落负责处理当前会话的复盘。

## 10. 技术改造计划

用户确认本方案后，建议按以下顺序执行。

### 10.1 后端

- 新增统一 `ReviewItem` 序列化层；
- 在 `session_view` 中返回 `review.items`；
- 将 `LearningCandidate` 转换为 `ReviewItem(source_type=memory/project_rule)`；
- 将 `EvolutionProposal` 转换为 `ReviewItem(source_type=assistant_workflow)`；
- 新增统一处理接口：
  - `POST /api/session/{id}/review/{item_id}/accept`
  - `POST /api/session/{id}/review/{item_id}/skip`
- 保留原 learning/evolution API 作为内部或兼容层，前端逐步不直接调用；
- 删除会话时可撤销当前 session 的 pending review items。

### 10.2 前端

- 移除独立 `learningPanel` 视觉入口；
- 将 `evolutionReviewBtn` 改名或重语义为 `sessionReviewBtn`；
- 徽标数量显示所有 pending review items；
- 弹窗改为统一 Review Modal；
- 每条 item 根据 `source_type` 显示不同类型标签、按钮文案和影响说明；
- 技术细节默认折叠，只在 assistant_workflow 中显示；
- 点击接受/跳过后自动进入下一条。

### 10.3 文案

必须避免工程化表达：

| 禁止 | 替代 |
| --- | --- |
| `harness/agents/canon_keeper.md` | 角色设定检查方式 |
| `target_component` | 会影响的协作环节 |
| `A/B evaluation` | 已用测试样例对比 |
| `LearningCandidate` | 可保存的偏好 |
| `manifest` | 工作方式改进记录 |

## 11. 验收标准

- 创作过程中不显示复盘入口，除非已有已完成会话的待处理项；
- 点击完成后，只出现角落小图标和数量徽标，不弹出大面板；
- 偏好沉淀和工作方式建议进入同一个复盘弹窗；
- 弹窗每次只展示一条建议；
- 每条都能说明：建议、原因、以后影响、适用范围；
- 接受或跳过都会进入下一条；
- 跳过不会影响长期记忆或 harness；
- 工作方式条目没有足够验证时不能直接应用；
- 设置页只管理长期结果，不承担当前会话复盘；
- 全量测试通过；
- 浏览器检查确认输入框下方没有重复面板。

## 12. 本设计对 EcRoom 初衷的意义

EcRoom 的目标不是让用户管理一堆系统设置，而是让用户感觉：

```text
我完成了一次创作；
系统理解了这次过程里哪些东西值得保留；
我可以轻量决定哪些进入以后；
系统不会擅自扩大我的话，也不会把工程细节丢给我；
下一次它确实会因为这些确认过的东西变得更顺手。
```

这才是本项目需要的“自进化”：不是自动、膨胀、不可解释的进化，而是由完成作品触发、由证据支撑、由用户确认、按作用域生效的协作成熟。
