# 临时 SSD：真实创作流程与复盘入口修正

本文件用于本轮体验修正。执行完成后，核心原则合并进 `ECROOM_SSD.md`。

## 1. 当前问题

当前实现有两个不自然点：

- 完成作品弹窗里加入 `查看本次复盘`，让复盘像“保存作品”的一个主动作，破坏了轻量小图标入口的设计；
- 首次生成阶段条会显示 `记忆沉淀`，看起来像系统从第一轮开始就在处理长期记忆，流程不真实。

这会让用户产生两个误解：

```text
系统是不是每次创作都先花时间做记忆沉淀？
完成作品是不是必须处理复盘？
```

真实产品逻辑应该相反：创作时优先完成作品，复盘只在完成后作为轻量待确认项出现。

## 2. 真实链路

### 2.1 创作中

创作中只展示和本次产出直接相关的阶段：

```text
需求理解
-> 资料检索 / 上下文召回
-> 创作策略
-> 初稿写作
-> 改稿整理
-> 质量评审
```

如果涉及平台、角色、世界观、禁用表达，可以展示更具体的检查项：

```text
平台边界检查
设定一致性检查
反馈定位
```

但不能展示长期 `记忆沉淀`，因为初次创作时还没有经过用户反馈验证，也没有完成态 commit 点。

### 2.2 后台观察

系统可以在创作中记录内部观察：

- 用户明确约束；
- 用户反复反馈；
- 草稿被修改的对象；
- 质量评审发现的问题；
- 平台或设定一致性风险。

这些观察只进入临时 observation buffer / evidence，不进入长期记忆，也不作为前台阶段显示。

### 2.3 完成后

用户点击 `完成话题` 后：

```text
保存完成状态
-> 生成少量 ReviewItem
-> 标题栏出现小图标入口
-> 用户可稍后点击处理
```

完成作品弹窗不再包含复盘按钮。它只负责作品去向：

- 发布作品；
- 只保存作品；
- 继续修改。

复盘入口只在对话标题栏或最后一条完成稿附近出现，形式是小图标/徽标，不能挤占主流程。

## 3. 入口设计

复盘入口采用轻量提醒：

```text
[小图标] 2
```

视觉要求：

- 位于对话标题右侧或完成稿角落；
- 有 pending 项时显示；
- 没有 pending 项时隐藏；
- hover/title 说明 `本次复盘：2 条可确认`；
- 不放入作品保存弹窗；
- 不自动弹出。

如果用户没有处理，pending 项保留在当前会话；用户返回该会话时仍可处理。

## 4. 复盘弹窗

复盘弹窗继续保留，但删掉补充说明输入框。

原因：

- 如果补充说明不进入保存内容，用户会困惑它有什么用；
- 如果进入保存内容，又会污染规则正文；
- 更成熟的做法是系统从用户选择、跳过、后续反馈和重复失败中判断，而不是让用户写审批备注。

弹窗只保留：

- 建议类型；
- 建议内容；
- 适用范围；
- 以后影响；
- `建议依据` 折叠区；
- `跳过` / `保存或允许`。

## 5. 建议依据

`建议依据` 只显示面向用户的解释，不显示工程字段。

允许显示：

- 你在这次创作里给出了明确约束或项目设定；
- 这次质量检查发现了设定一致性风险；
- 这条只会在当前项目或类似任务中生效；
- 跳过不会影响当前作品。

禁止显示：

- candidate id；
- target object；
- confidence；
- harness 路径；
- validation plan；
- rollback plan；
- source_type / project_rule 等内部字段。

## 6. 工作流阶段规则

### 初始生成阶段

最多展示 5-6 个阶段：

```text
需求理解
资料检索
创作策略
初稿写作
改稿整理
质量评审
```

`资料检索` 文案应按任务动态变化：

- 有 URL：`读取链接和资料库`；
- 有平台：`召回平台语境和资料库`；
- 无外部资料：`召回相关项目资料和记忆`。

### 继续修改阶段

继续修改不应展示完整新创作流程，而是：

```text
反馈定位
上下文对齐
改稿整理
质量复核
反馈沉淀
```

若用户明确补充规则，可以显示：

```text
约束更新
```

这里允许显示 `反馈沉淀`，但它的语义必须明确：记录这次反馈改变了什么，作为本会话后续改稿和完成后复盘依据；它不等于立刻写入长期偏好。

## 7. 用户介入自动化的真实位置

用户介入不发生在生成阶段，而发生在完成后：

```text
创作中：用户通过反馈介入作品
完成后：用户通过复盘介入系统后续行为
长期：用户在设置中管理已保存偏好和工作规则
```

这三种介入不能混在一个 loading 阶段里展示。

## 7.1 Skill 生命周期

技能包是初次生成的创作启动包，不是同一会话里每次反馈都重复调用的按钮。

```text
初次生成
  -> 使用用户选择的 skill package
  -> 形成初始路线、约束、评价标准和输出 contract

后续反馈
  -> 不再自动注入“使用技能”
  -> 使用当前稿件、用户反馈、会话上下文和初始 skill 留下的约束改稿
  -> 记录反馈沉淀，供后续复盘
```

反馈输入区不展示 skill 选择按钮。用户要换创作模式，应开启新会话或在文本中明确提出新的任务方向，而不是在同一稿件上反复叠加 skill。

产品化细节：

- 首次创建页和灵感创建页保留 `使用技能`，因为这里是在选择新内容项目的启动方式；
- 进入会话后的反馈输入区不展示 `使用技能`，避免用户以为每次改稿都要重新选择工具；
- 初始 skill 运行后转化为会话上下文、约束和评价标准，而不是持续可见的工具状态；
- 后续反馈只显示 `反馈定位 -> 上下文对齐 -> 改稿整理 -> 质量复核 -> 反馈沉淀`；
- `反馈沉淀` 是本会话记录，不等于立刻写入长期记忆；
- 反馈里出现 `使用技能：xxx` 时视为技术指令噪声，不写入偏好、规则或长期记忆；
- 多 skill 只在初次生成时组合，必须有 primary / supporting / suppressed，避免多个模式互相抢任务。

## 8. 本轮实现清单

- 删除完成作品弹窗里的复盘提示和按钮；
- 删除复盘弹窗的补充说明 textarea；
- 前端 accept/skip 不再发送 reviewer_note；
- 标题栏复盘入口改回小图标 + 徽标；
- 初始生成 workflow preview 不包含 Memory Curator；
- 前端初次生成 fallback workflow 不包含长期 `记忆沉淀`；
- 继续修改 fallback workflow 改成反馈定位链路，并包含 `反馈沉淀`；
- 反馈输入区隐藏 skill 入口，且反馈提交不再注入 `使用技能`；
- 后端过滤反馈文本里的 `使用技能：xxx`，避免误沉淀为偏好或项目规则；
- 增加回归测试覆盖反馈阶段不重复激活/沉淀 skill 指令；
- SSD 合并上述真实链路规则；
- 测试和运行态检查通过。
